# Руководство пользователя AI Development OS — от ТЗ до хостинга

**Статус:** руководство к `0.2.0-draft` (ветка `main`). Методология пока **не прошла реальный пилот** ChatGPT Web + Codex Desktop; это рабочий процесс, а не доказанная система автоматических гарантий. **Этот файл для человека**, не обязательный промпт, не новый агент и не требование создавать документы на каждом шаге.

## 1. Суть за минуту

**Пользователь** — владелец продукта и разрешений: приносит ТЗ, подтверждает ключевые решения, выбирает следующий результат, принимает работу, отдельно разрешает публикацию.

**ChatGPT Web** — ведущий аналитик и архитектор: уточняет исходные требования, спорит с неоправданными техническими решениями, проектирует минимальный MVP, декомпозирует путь до хостинга, выбирает подходящую сложность модели, выдаёт **одну согласованную задачу Codex**, проверяет реальные доказательства.

**Codex Desktop** — исполнитель в **конкретном продуктовом репозитории**: читает необходимое, меняет только разрешённые пути, запускает проверки и Git, сообщает DONE / PARTIAL / BLOCKED и **останавливается**. Следующий пункт плана не запускает сам.

Цикл: **ТЗ → подтверждённое поведение → минимальный план и вертикальные задачи → одна задача Codex → diff/тесты → приёмка → следующая задача → staging → отдельное разрешение production → наблюдение и доработка**.

Правила методологии находятся в `CORE.md` (инструкции ChatGPT Project), `MANIFEST.md` (выбор модулей) и нужных модулях. Не загружай всю библиотеку для каждого вопроса.

## 2. Маршрутизация моделей: кто реально «тянет» работу

**Сначала проверяй доступность в фактическом интерфейсе.** Названия ниже — ориентиры возможностей по опубликованной линейке, а не обещание доступа, автоматического переключения модели из промпта или обязательное использование API. Режим задачи FAST / STANDARD / CONTROLLED определяет **риск и проверки**, а не интеллект модели.

| Уровень | ChatGPT Web (если доступен GPT-6) | Codex Desktop (если модель доступна в селекторе) | Для чего |
|---|---|---|---|
| **Быстрый** | GPT-6 **Instant** | **Luna** или доступный быстрый/default | Простое извлечение требований, форматирование, локальные понятные правки, мелкие тесты и документация |
| **Рабочий** | GPT-6 **Medium** | **Terra** для узких понятных/экранных задач; **Sol** для стандартной реализации | Уточнение ТЗ, постановка задач, обычная функция, UI/API, тесты, исправления с ясной причиной |
| **Сложный** | GPT-6 **High** | **Sol** с повышенным effort; **Astra** для действительно трудных задач | Архитектура, сложные зависимости, опасная миграция, корневая причина неисправности, security/release-план |
| **Независимая проверка** | Medium/High с **реальным diff, тестами и фактическими логами** | Повторная проверка/диагностика только в отдельной утверждённой задаче | Найти неверные предположения и нарушения контрактов; другой ответ модели сам по себе не доказательство |

**Практическое правило:** начинай с минимально достаточного уровня. Если результат неверен, сначала улучши факты, контекст, декомпозицию и проверку; повышай модель/effort, когда **причина именно в сложности рассуждения**. Не держи самую дорогую/сильную модель на простых задачах. Для опасных, но простых действий усиливаются **контроль и разрешения**, а не обязательно интеллект. Если нужной модели нет, используй ближайшую доступную, уменьши задачу и сохрани критерии проверки. ChatGPT/AGENTS не могут сами менять ручной выбор модели в UI.

**Важно:** `GPT-6` в ChatGPT и `GPT-6 Astra / GPT-6.1 Sol / Terra / Luna` в API/Codex — не одна универсальная кнопка. Доступность и названия зависят от продукта, плана, версии приложения и выбора в интерфейсе. Default/Auto оставляй, если он наблюдаемо работает; не устанавливай новые AI-агенты, Skills или модельный оркестратор только для этой таблицы.

## 3. Полный маршрут разработки — от идеи до эксплуатации

Это **карта этапов**, а не команда запускать все этапы сразу. Каждый этап допускает несколько маленьких, последовательно согласуемых задач. При появлении новых фактов Web меняет план. Стек, хостинг и число задач определяются **реальным ТЗ**, не шаблоном.

| № | Этап и конечный результат | Кто ведёт / уровень модели | Выход и условие перехода |
|---|---|---|---|
| **0** | **Входное ТЗ:** что нужно клиенту, ограничения, реальные данные, бюджет, срок, кто подтверждает изменения | Web, Medium; High при противоречиях | Список CONFIRMED / UNKNOWN / CONFLICTING, измеримые критерии приемки, вопросы только по блокирующим решениям; **не писать код** |
| **1** | **MVP:** минимальный полезный пользовательский сценарий и разумные исключения | Web, High для сложного выбора; Medium для ясного ТЗ | Утверждённые границы MVP, приоритеты, подходящий уровень качества продукта, явное «не делаем пока» |
| **2** | **Архитектура:** минимальный стек, хранение, интерфейсы, интеграции, путь запуска и предполагаемый способ размещения | Web, High при неоднозначности; при простом проекте Medium | Короткий Blueprint/PROJECT; без микросервисов, очередей и абстракций «на вырост»; утверждение ключевых решений |
| **3** | **Подготовка репозитория и среды:** Git, AGENTS, запуск, зависимости, быстрая проверка, секреты и границы доступа | Web ставит ограниченную задачу; Codex Sol/Default; для инвентаризации — read-only | Отчёт о реальном состоянии, затем **отдельно утверждённый** bootstrap; команда `verify` или честно обозначенная причина её отсутствия, исходный SHA и статус |
| **4** | **Реализация MVP:** по одной вертикальной проверяемой пользовательской функции | Web Medium для постановки, High только при сложных решениях; Codex Terra/Sol; Astra при доказанной трудности | Для каждого среза: одна цель, список разрешённых изменений, тест/проверка, дифф, краткий отчёт, решение ACCEPT/FIX/REWORK, затем STOP |
| **5** | **Интеграция и качество:** пользовательские сценарии целиком, ошибки, данные, совместимость, доступность по необходимости | Web Medium/High; Codex Sol, Astra для сложной диагностики | Проверен MVP end-to-end, устранены блокирующие ошибки, не ослаблены тесты ради зелёного результата; риск-ориентированная проверка, а не абстрактное «100% покрытие» |
| **6** | **Готовность к размещению:** выбрать подходящий хостинг, домен, БД/хранилище, переменные среды, секреты, HTTPS, логи, резервное копирование/восстановление при наличии важных данных | Web High для решений с ценой или риском; Codex Sol для воспроизводимой конфигурации | Документирован выбранный способ деплоя, стоимость/лимиты, staging, критерий работоспособности, план отката; **разрешение владельца** |
| **7** | **Staging:** развернуть тестовую копию и проверить в среде, похожей на рабочую | Web задаёт один шаг, Codex Sol при настроенных разрешениях, иначе оператор | Реальный URL/доступ, smoke-тесты, проверка конфигурации без раскрытия секретов, миграций и внешних интеграций. Ошибки — новая ограниченная задача |
| **8** | **Production:** явное «публикуем», контрольный чек, деплой, проверка после выпуска | Web High для плана и проверки риска; Codex только в явно согласованной роли либо человек-оператор | Отдельное подтверждение пользователем, рабочий URL/домен, HTTPS, реальный health-check, проверка ключевого сценария и доступный план возврата |
| **9** | **После релиза:** наблюдение, обратная связь, инциденты, резервные копии и следующая версия | Web Medium для приоритизации; Codex Terra/Sol для локальных исправлений, High/Astra для сложных проблем | Наблюдаемые факты, короткий backlog, одна согласованная следующая задача. Повторять цикл без автоматического расширения scope |

**Не каждый продукт требует** отдельной БД, CI, Docker, staging-сервера, монитора, миграций или платного хостинга. Для статического MVP достаточно статического деплоя и smoke-проверки. Для приложения с пользовательскими данными нужны соответствующие реальные меры безопасности, сохранности и восстановления.

## 4. Как декомпозировать конкретный продукт

Сначала Web описывает **весь путь до хостинга на уровне вех** (какой результат когда нужен), потом детализирует только ближайшие **3–5 проверяемых вертикальных срезов**. В Codex отправляет **только первый утверждённый**.

Хороший срез: «Пользователь может создать запись через форму; запись сохраняется и видна после перезагрузки; есть проверка одного успешного и одного ошибочного сценария». Плохой срез: «Напиши всю backend-архитектуру» или искусственные задачи «создай тип», «создай файл», которые нельзя осмысленно принять по отдельности.

**Каждая задача Codex имеет:** один наблюдаемый результат; контекст и что можно читать; **WRITE ALLOWLIST**; что менять запрещено; критерии приёмки; команду проверки; сведения о Git/исходных изменениях; условия остановки; формат короткого отчёта. Если нужных путей не знаем — сначала **одна read-only разведка**, а не догадка. Задача может менять несколько файлов, когда это один связный результат.

**Выполнение:** Codex работает с фактическим Git-репозиторием, запускает проверку, показывает реальные изменённые пути (включая staged/unstaged/untracked), пишет DONE / PARTIAL / BLOCKED и останавливается. Если требуется новый файл, библиотека, изменение API, доступ к production или выход за разрешённый scope — **BLOCKED до нового разрешения**. Это поведенческое правило, **не гарантированная файловая блокировка**.

**Приёмка:** Web/пользователь независимо сравнивает diff и реальные проверки с договорённостью, не верит одной фразе «всё работает». Для рискованных работ используй подтверждённые CI/проверку оператора/безопасную среду. Пропущенная проверка помечается NOT RUN, не PASS.

## 5. Как пользоваться каждый день

### В каком чате работаем

ChatGPT Web **сам рекомендует структуру чатов** и сообщает её в начале содержательного ответа: `ЧАТ: 01 — ТЗ и архитектура | ЭТАП: анализ ТЗ`, затем `ДЕЙСТВИЕ: продолжаем здесь` или `ДЕЙСТВИЕ: открыть новый чат`. При переходе, например, в `02 — Разработка MVP`, он выдаёт название нового чата и **готовый стартовый промпт с проверенными фактами**. Новый чат нужен по реальной причине, а не после каждой микрозадачи. Web не может утверждать, что создал или переключил чат самостоятельно.

Всякий раз, когда Web выдаёт задачу Codex, он явно подписывает, куда вставлять сообщение: `КУДА ВСТАВИТЬ: Codex Desktop → текущий чат` или `Codex Desktop → новый чат` и объясняет причину. Это рекомендации для пользователя; ни инструкции Web, ни `AGENTS.md` не управляют переключением окон приложения.


### Один раз для нового проекта

1. В ChatGPT Web создай отдельный **Project** для продукта; помести `CORE.md` в **Project Instructions**, а `MANIFEST.md` и нужные материалы держи доступными через GitHub/файлы. Уточни, какая версия реально загружена. Это не обновляется автоматически после каждого коммита методологии.
2. Передай **исходное ТЗ**, а не абстрактное «сделай сайт». Web возвращает вопросы о критических пробелах, краткий MVP/архитектуру, карту пути до хостинга, модельный маршрут и ближайшие срезы.
3. Утверди требования и основные решения. Существующий проект: сначала read-only обследование Codex. Новый: отдельная утверждённая настройка проекта в Codex (AGENTS, Git, запуск, baseline).
4. Дальше используй короткий повторяемый цикл ниже. Не нужно каждый раз создавать новый файл, чат или полный отчёт.

### Сообщения, которые можно копировать

**Старт проекта — в ChatGPT Web:**

```text
У нас новый продукт. Работаем по AI Development OS из инструкций проекта.
ТЗ ниже. Не начинай кодить. Выдели подтверждённые и неясные требования,
предложи самый короткий жизнеспособный MVP и архитектуру без оверинжиниринга.
Дай карту этапов до хостинга, 3–5 ближайших проверяемых срезов, риски,
рекомендации по доступным моделям/effort для Web и Codex.
Задай только вопросы, без которых нельзя принять существенное решение.
Ничего не выдавай в Codex до моего утверждения.
ТЗ: <вставить>
```

**Следующая задача — в ChatGPT Web:**

```text
Вот актуальные проверенные PROJECT/TODO/требования, Git-состояние и итог
предыдущей задачи. Выбери одну следующую вертикальную задачу из согласованного
плана. Если не знаешь файлов — сначала read-only разведка.
Дай один готовый промпт для Codex: цель, READ CONTEXT, WRITE ALLOWLIST,
запреты, приёмка, VERIFY, Git/base, условия BLOCKED и STOP.
Рекомендуй минимально достаточный доступный уровень модели.
```

**Запуск — в Codex Desktop:** открой нужный продуктовый репозиторий, посмотри фактическую доступную модель/default, вставь **один** промпт Web и проверь область изменений. Не передавай весь roadmap как команду к исполнению.

**Приёмка — обратно в ChatGPT Web:**

```text
Вот отчёт Codex, фактический git status/diff, команды и exit codes.
Проверь критерии приёмки и WRITE ALLOWLIST. Отдели подтверждённое
от самоотчёта. Вердикт ACCEPT / FIX / REWORK / INSUFFICIENT EVIDENCE.
Если принятие возможно — кратко обнови прогресс и предложи,
но не запускай, только одну следующую задачу.
```

**Перед хостингом — в ChatGPT Web:**

```text
MVP проверен. Предложи минимальный план staging → production под фактический
стек, бюджет и тип данных: провайдер/лимиты, конфигурация, DNS/HTTPS,
секреты, нужные бэкапы, smoke/health, откат и наблюдение.
Раздели подготовку, тестовый деплой и production на отдельные решения/задачи.
Не выдавай Codex доступ к production и ничего не публикуй без
моего явного согласия.
```

## 6. Хостинг: граница ответственности

До выбора хостинга Web должен знать **тип продукта, стек, пользовательские данные, региональные/юридические ограничения, бюджет, трафик, требуемую доступность**. Не навязывай провайдера и не выдумывай цены, тарифы или доступ. Codex может подготовить Dockerfile/конфиг/документацию **только по утверждённому заданию**. Staging и production — разные операции, даже если у малого проекта используется один провайдер.

**Безопасный порядок:** (1) план и способ возврата → (2) ревью конфигурации → (3) staging → (4) реальные smoke-проверки → (5) отдельное «разрешаю production» с названной целью → (6) контролируемый деплой → (7) проверка URL, TLS, ключевых действий и логов → (8) запись фактического результата. Никогда не публикуй реальные секреты в промптах/отчётах; выдавай минимальные права или деплой выполняй сам. `git push`, миграции, удаление данных и изменение production не разрешаются автоматически фактом завершения кода.

Если продакшен-проверка не прошла, **остановись**; решение об откате должно учитывать текущие данные и проверенный способ восстановления. Не применять `git reset --hard` или удаление БД «для очистки».

## 7. Как понять, что система помогает, а не тормозит

Для первых реальных задач замерь: сколько ручных переходов между Web/Codex, сколько задач принято с первого раза, сколько выходов за scope, были ли ложные PASS, сколько времени ушло на реальные проверки. Запускай сначала три теста из `TEST_CASES.md`: T03 (маленькая задача), T37+T08 (ловушка scope и независимая проверка), T15 (восстановление контекста). На момент написания всё **NOT RUN**.

### Как система сама выбирает улучшение

После реальной неудачи, повторной переделки, потери контекста или обнаруженного узкого места ChatGPT Web **сам предлагает наиболее перспективное направление** — не ждёт, пока ты назовёшь инструмент. Он сравнивает 2–3 альтернативы, в том числе **оставить как есть**, по ожидаемой пользе, уверенности в гипотезе, цене, простоте проверки, риску и обратимости. Затем рекомендует **только один** минимальный эксперимент: исходное наблюдение, гипотеза, контрольный вариант, метрика, критерий успеха/неудачи, цена и способ отмены. Если проблема не наблюдалась — эксперимент не нужен; если нет исходных данных — первый эксперимент состоит в безопасном измерении.

**Пример с Honcho:** если новые чаты Codex действительно теряют важные решения, сначала измеряем восстановление контекста при текущих `AGENTS.md` + `PROJECT.md`/`TODO.md` на одинаковых тестовых задачах. Только при подтверждённых потерях предлагаем ограниченный эксперимент с Honcho **на вымышленных данных**, с отдельным разрешением на установку и внешнюю передачу информации. Сравниваем число правильных восстановленных решений, ручных подсказок и трудозатраты. Не стало измеримо лучше — Honcho не добавляем.

Web может самостоятельно **выбирать и аргументировать**, но не запускает изменения проекта, платные API, новые зависимости или публикацию без разрешения. Codex получает одну согласованную задачу и останавливается после отчёта. Результат `PASS / FAIL / INCONCLUSIVE / NOT RUN` фиксируется только по реальным данным в уже существующем TODO/Decision либо в тестах методологии, без нового «менеджера экспериментов».

**Не требуется по умолчанию:** отдельный AI-оркестратор, несколько параллельных агентов, обязательный `STATE.md`, новый Skill на каждый этап, отдельный документ для каждой задачи, фиксированное число файлов или новый Codex-чат после каждой правки. Добавлять только после измеренной необходимости.
