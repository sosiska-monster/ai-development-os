# Руководство пользователя AI Development OS — от ТЗ до хостинга

**Статус:** руководство к `0.2.0-draft` (ветка `main`). Методология пока **не прошла реальный пилот** ChatGPT Web + Codex Desktop; это рабочий процесс, а не доказанная система автоматических гарантий. **Этот файл для человека**, не обязательный промпт, не новый агент и не требование создавать документы на каждом шаге.

## 1. Суть за минуту

**Пользователь** — владелец продукта и разрешений: приносит ТЗ, подтверждает ключевые решения, выбирает следующий результат, принимает работу, отдельно разрешает публикацию.

**ChatGPT Web** — ведущий аналитик и архитектор: уточняет исходные требования, спорит с неоправданными техническими решениями, проектирует минимальный MVP, декомпозирует путь до хостинга, выбирает подходящую сложность модели, выдаёт **одну согласованную задачу Codex**, проверяет реальные доказательства.

**Codex Desktop** — исполнитель в **конкретном продуктовом репозитории**: читает необходимое, меняет только разрешённые пути, запускает проверки и Git, сообщает DONE / PARTIAL / BLOCKED и **останавливается**. Следующий пункт плана не запускает сам.

Цикл: **ТЗ → подтверждённое поведение → минимальный план и вертикальные задачи → одна задача Codex → diff/тесты → приёмка → следующая задача → staging → отдельное разрешение production → наблюдение и доработка**.

Правила методологии находятся в `CORE.md` (инструкции ChatGPT Project), `MANIFEST.md` (выбор модулей) и нужных модулях. Не загружай всю библиотеку для каждого вопроса.

## 2. Маршрутизация моделей: кто реально «тянет» работу

**Сначала проверяй доступность в фактическом интерфейсе.** Названия ниже — ориентиры возможностей по опубликованной линейке, а не обещание доступа, автоматического переключения модели из промпта или обязательное использование API. Режим задачи FAST / STANDARD / CONTROLLED определяет **риск и проверки**, а не интеллект модели.

| Уровень | ChatGPT Web (если доступен GPT-6) | Codex Desktop (если модель доступна в селекторе) | Для чего |
|---|---|---|---|
| **Быстрый** | GPT-6 **Instant** | **Luna** или доступный быстрый/default | Простое извлечение требований, форматирование, локальные понятные правки, мелкие тесты и документация |
| **Рабочий** | GPT-6 **Medium** | **Terra** для узких понятных/экранных задач; **Sol** для стандартной реализации | Уточнение ТЗ, постановка задач, обычная функция, UI/API, тесты, исправления с ясной причиной |
| **Сложный** | GPT-6 **High** | **Sol** с повышенным effort; **Astra** для действительно трудных задач | Архитектура, сложные зависимости, опасная миграция, корневая причина неисправности, security/release-план |
| **Независимая проверка** | Medium/High с **реальным diff, тестами и фактическими логами** | Повторная проверка/диагностика только в отдельной утверждённой задаче | Найти неверные предположения и нарушения контрактов; другой ответ модели сам по себе не доказательство |

**Практическое правило:** начинай с минимально достаточного уровня. Если результат неверен, сначала улучши факты, контекст, декомпозицию и проверку; повышай модель/effort, когда **причина именно в сложности рассуждения**. Не держи самую дорогую/сильную модель на простых задачах. Для опасных, но простых действий усиливаются **контроль и разрешения**, а не обязательно интеллект. Если нужной модели нет, используй ближайшую доступную, уменьши задачу и сохрани критерии проверки. ChatGPT/AGENTS не могут сами менять ручной выбор модели в UI.

**Важно:** `GPT-6` в ChatGPT и `GPT-6 Astra / GPT-6.1 Sol / Terra / Luna` в API/Codex — не одна универсальная кнопка. Доступность и названия зависят от продукта, плана, версии приложения и выбора в интерфейсе. Default/Auto оставляй, если он наблюдаемо работает; не устанавливай новые AI-агенты, Skills или модельный оркестратор только для этой таблицы.

## 3. Полный маршрут разработки — от идеи до эксплуатации

Это **карта этапов**, а не команда запускать все этапы сразу. Каждый этап допускает несколько маленьких, последовательно согласуемых задач. При появлении новых фактов Web меняет план. Стек, хостинг и число задач определяются **реальным ТЗ**, не шаблоном.

| № | Этап и конечный результат | Кто ведёт / уровень модели | Выход и условие перехода |
|---|---|---|---|
| **0** | **Входное ТЗ:** что нужно клиенту, ограничения, реальные данные, бюджет, срок, кто подтверждает изменения | Web, Medium; High при противоречиях | Список CONFIRMED / UNKNOWN / CONFLICTING, измеримые критерии приемки, вопросы только по блокирующим решениям; **не писать код** |
| **1** | **MVP:** минимальный полезный пользовательский сценарий и разумные исключения | Web, High для сложного выбора; Medium для ясного ТЗ | Утверждённые границы MVP, приоритеты, подходящий уровень качества продукта, явное «не делаем пока» |
| **2** | **Архитектура:** минимальный стек, хранение, интерфейсы, интеграции, путь запуска и предполагаемый способ размещения | Web, High при неоднозначности; при простом проекте Medium | Короткий Blueprint/PROJECT; без микросервисов, очередей и абстракций «на вырост»; утверждение ключевых решений |
| **3** | **Подготовка репозитория и среды:** Git, AGENTS, запуск, зависимости, быстрая проверка, секреты и границы доступа | Web ставит ограниченную задачу; Codex Sol/Default; для инвентаризации — read-only | Отчёт о реальном состоянии, затем **отдельно утверждённый** bootstrap; команда `verify` или честно обозначенная причина её отсутствия, исходный SHA и статус |
| **4** | **Реализация MVP:** по одной вертикальной проверяемой пользовательской функции | Web Medium для постановки, High только при сложных решениях; Codex Terra/Sol; Astra при доказанной трудности | Для каждого среза: одна цель, список разрешённых изменений, тест/проверка, дифф, краткий отчёт, решение ACCEPT/FIX/REWORK, затем STOP |
| **5** | **Интеграция и качество:** пользовательские сценарии целиком, ошибки, данные, совместимость, доступность по необходимости | Web Medium/High; Codex Sol, Astra для сложной диагностики | Проверен MVP end-to-end, устранены блокирующие ошибки, не ослаблены тесты ради зелёного результата; риск-ориентированная проверка, а не абстрактное «100% покрытие» |
| **6** | **Готовность к размещению:** выбрать подходящий хостинг, домен, БД/хранилище, переменные среды, секреты, HTTPS, логи, резервное копирование/восстановление при наличии важных данных | Web High для решений с ценой или риском; Codex Sol для воспроизводимой конфигурации | Документирован выбранный способ деплоя, стоимость/лимиты, staging, критерий работоспособности, план отката; **разрешение владельца** |
| **7** | **Staging:** развернуть тестовую копию и проверить в среде, похожей на рабочую | Web задаёт один шаг, Codex Sol при настроенных разрешениях, иначе оператор | Реальный URL/доступ, smoke-тесты, проверка конфигурации без раскрытия секретов, миграций и внешних интеграций. Ошибки — новая ограниченная задача |
| **8** | **Production:** явное «публикуем», контрольный чек, деплой, проверка после выпуска | Web High для плана и проверки риска; Codex только в явно согласованной роли либо человек-оператор | Отдельное подтверждение пользователем, рабочий URL/домен, HTTPS, реальный health-check, проверка ключевого сценария и доступный план возврата |
| **9** | **После релиза:** наблюдение, обратная связь, инциденты, резервные копии и следующая версия | Web Medium для приоритизации; Codex Terra/Sol для локальных исправлений, High/Astra для сложных проблем | Наблюдаемые факты, короткий backlog, одна согласованная следующая задача. Повторять цикл без автоматического расширения scope |

**Не каждый продукт требует** отдельной БД, CI, Docker, staging-сервера, монитора, миграций или платного хостинга. Для статического MVP достаточно статического деплоя и smoke-проверки. Для приложения с пользовательскими данными нужны соответствующие реальные меры безопасности, сохранности и восстановления.

## 4. Как декомпозировать конкретный продукт

**Сначала строим дерево от конечного результата, а не список технологий.** Web читает ТЗ и формулирует корень `G0: готовый продукт по пониманию заказчика` с конкретным сценарием приёмки. У корня могут быть дочерние результаты (подсистемы/сценарии); они разбиваются на небольшие проверяемые задачи. Помимо вложенности `PARENT` отдельно фиксируются зависимости `DEPENDS_ON`, потому что одна задача может зависеть от двух ветвей дерева. Вместе получается дерево результатов + DAG порядка работ, без циклов.

Пример **условного** ML-проекта (реальные пропорции, метрики и условия задаёт заказчик/пользователь):

```text
G0 — Готовый ML-продукт: модель решает задачу заказчика [приёмка утверждается]
  G1 — Данные пригодны к обучению
    T1 — Проверить состав и происхождение датасета
    T2 — Утвердить стратегию train/val/test [решение пользователя]
    T3 — Создать и проверить выборки [depends: T1, T2]
  G2 — Рабочее обучение
    T4 — Реализовать обучающий путь [depends: T3]
    T5 — Получить проверенный checkpoint [depends: T4]
  G3 — Доказанное качество
    T6 — Проверить метрики без утечки [depends: T3, T5]
  G4 — Проверенный пользовательский сценарий
    T7 — Собрать и проверить готовое решение [depends: T5, T6]
G0 ACCEPTED только после сквозной приёмки решения, а не после семи отчётов DONE.
```

**Одна версия графа:** описание готового продукта/приёмки хранится в `PROJECT.md` или подтверждённых требованиях продукта; узлы и связи — в существующем `TODO.md` (либо согласованном эквиваленте) как `ID | PARENT | REQ | ACCEPTANCE | DEPENDS_ON | STATUS | EVIDENCE`. Web может нарисовать Mermaid, но не должен держать отдельную рассинхронизированную копию графа. Подробно планирует только ближайшие несколько задач, остальные обозначает результатами. По отчёту Codex Web проверяет GitHub/CI-данные, обновляет статус связанного узла и выбирает следующую `READY`-задачу; **выполняется только одна утверждённая**.

При изменении ТЗ Web пересматривает корень/ветви и отмечает связанные задачи и проверки для пересмотра, вместо продолжения устаревшего плана. Эксперимент помечается отдельно, не считается необходимой частью продукта до твоего решения. **Если в ТЗ нет критериев готового продукта, их нужно выяснить до полного разбиения на задачи**; Codex может только предложить технические зависимости по реальному репозиторию в read-only режиме.

Сначала Web описывает **весь путь до хостинга на уровне вех** (какой результат когда нужен), потом детализирует только ближайшие **3–5 проверяемых вертикальных срезов**. В Codex отправляет **только первый утверждённый**.

Хороший срез: «Пользователь может создать запись через форму; запись сохраняется и видна после перезагрузки; есть проверка одного успешного и одного ошибочного сценария». Плохой срез: «Напиши всю backend-архитектуру» или искусственные задачи «создай тип», «создай файл», которые нельзя осмысленно принять по отдельности.

**Каждая задача Codex имеет:** один наблюдаемый результат; контекст и что можно читать; **WRITE ALLOWLIST**; что менять запрещено; критерии приёмки; команду проверки; сведения о Git/исходных изменениях; условия остановки; формат короткого отчёта. Если нужных путей не знаем — сначала **одна read-only разведка**, а не догадка. Задача может менять несколько файлов, когда это один связный результат.

**Выполнение:** Codex работает с фактическим Git-репозиторием, запускает проверку, показывает реальные изменённые пути (включая staged/unstaged/untracked), пишет DONE / PARTIAL / BLOCKED и останавливается. Если требуется новый файл, библиотека, изменение API, доступ к production или выход за разрешённый scope — **BLOCKED до нового разрешения**. Это поведенческое правило, **не гарантированная файловая блокировка**.

**Приёмка:** Web/пользователь независимо сравнивает diff и реальные проверки с договорённостью, не верит одной фразе «всё работает». Для рискованных работ используй подтверждённые CI/проверку оператора/безопасную среду. Пропущенная проверка помечается NOT RUN, не PASS.

### Сначала Web показывает решение — затем отправляет его Codex

**Вариант 1: «Сделай страницу тарифов».** Это цель, а не утверждённый дизайн. Web самостоятельно формирует 1 конкретный рекомендуемый вариант: пример структуры карточек, описание расположения на компьютере/телефоне, главные действия пользователя, состояния и критерии удобства. При необходимости показывает текстовый wireframe/визуальный предварительный макет. Вопрос «как ты хочешь, чтобы выглядело?» не подменяет инициативное проектирование. Максимум ещё 1–2 варианта, только если это помогает выбору.

**Вариант 2: «Три тарифа с утверждёнными ценами, функциями и периодом оплаты».** Web сохраняет указанные бизнес-параметры как CONFIRMED (с указанием источника/полномочий), а **сам предлагает дизайн страницы**: какие тарифы выделять, как сравнивать, где CTA, как работает мобильная версия. Не выдумывает скидки, реальные цены, возможности тарифов и обещания. Незаполненные данные помечает TBD/NEEDS_DECISION; демонстрационные примеры — только с явным указанием «не согласовано».

Цикл: `задача в Product Goal Graph → Web PROPOSED-макет + поведение → твоя правка/одобрение → короткая утверждённая спецификация и статус READY → одна Codex-задача → фактическая UI-приёмка по утверждённому дизайну`. До согласования значимого оформления узел остаётся `DESIGN_REVIEW`, а не отправляется на реализацию. После согласования Codex может самостоятельно выбирать локальные технические детали, но не изменять тарифы и принципиальную структуру. При наличии уже утверждённого дизайн-компонента либо мелкой правке не создавай лишний раунд согласований.

Этот этап применяется не только к UI: для расплывчатой функции Web предлагает **проверяемый сценарий поведения** (вход, действия, ожидаемый результат и ограничения), а не отправляет Codex неопределённую команду.

## 5. Как пользоваться каждый день

### Куда отправлять промпт: точные имена чатов и постоянный реестр

**Web называет конкретный чат, а не YES/NO или «текущий/новый».** Чат — это рабочая зона с собственной ответственностью. Web ведёт компактный реестр имён/ролей/статусов и Git-сред в разделе `Chat Register` существующего **PROJECT.md продукта** или его доступной копии среди источников ChatGPT Project. Он не хранит всю переписку; история назначения чатов — это несколько проверенных строк. При изменении маршрута Web предлагает обновлённые строки и, если нет разрешённой записи через инструмент, просит тебя сохранить их. Файл/копия должны быть доступны каждому новому Web-чату; ChatGPT не видит автоматически незагруженные локальные файлы или все чужие чаты.

Пример **плана имён** (не утверждение, что эти чаты уже созданы):

| Точное имя чата | Где | За что отвечает | Git | Статус |
|---|---|---|---|---|
| `01 — ТЗ и архитектура` | ChatGPT Web | требования и одобренные решения | N/A | PROPOSED |
| `02 — Разработка MVP` | ChatGPT Web | основная очередь задач и приёмка | `main` / согласованная рабочая ветка | PROPOSED |
| `Codex — MVP разработка` | Codex Desktop | выполняет только очередную утверждённую задачу | проверенная основная рабочая ветка | PROPOSED |
| `03 — Эксперимент: модель X` | ChatGPT Web | гипотеза, измерения, вывод | `experiment/model-x` | PROPOSED |
| `Codex — Тест модели X` | Codex Desktop | тест в отдельном worktree | `experiment/model-x` | PROPOSED |
| `04 — Релиз и хостинг` | ChatGPT Web | staging, выпуск и проверки | утверждается отдельно | PROPOSED |

После реального создания чата пользователь подтверждает точное имя, Web помечает его `ACTIVE`. Завершённый эксперимент становится `ARCHIVED`; его ответственность и проверенный результат остаются в реестре. Не создавать все эти чаты сразу — только по потребности, и не открывать новый для каждого мелкого исправления. Если Web не может прочитать актуальный реестр, он прямо сообщает об этом, а не выдумывает историю.

**Формат передачи:**

```text
КУДА ВСТАВИТЬ: ChatGPT Web → «03 — Эксперимент: модель X»
ДЕЙСТВИЕ: СОЗДАТЬ (предлагаемое имя) / ПРОДОЛЖИТЬ (подтверждённое имя)
ЗОНА РАБОТЫ: проверка одной модели, не основная разработка
КУДА ПОЙДЁТ CODEX-ЗАДАНИЕ: Codex Desktop → «Codex — Тест модели X»
GIT: отдельный worktree, ветка experiment/model-x; main не изменять
```

Если чат нужно создать, Web даёт готовый стартовый промпт с подтверждёнными требованиями, проверенным состоянием Git и целью, но не заявляет, что сам создал/переименовал чат.

### Полностью изолированный эксперимент с нейросетью

1. В чате разработки Web замечает перспективную гипотезу и **сам выбирает** дешёвый проверяемый эксперимент. Сначала сравнивает его с «ничего не менять» и более простыми вариантами; ты утверждаешь эксперимент.
2. Если тест **только читает данные и рассуждает**, достаточно отдельного Web-чата и безопасных фиктивных данных, без новой ветки. Если установка модели, код, конфигурация или файлы могут меняться, Web выдаёт отдельную задачу настройки **изолированного тестового репозитория или Git worktree** с веткой `experiment/model-x`. Все изменения и установки должны остаться там или в отдельном тестовом окружении; одна Git-ветка сама по себе не изолирует глобально установленное ПО, базы данных и внешние API.
3. Перед выполнением Codex обязан проверить путь к папке, ветку, HEAD и dirty-файлы. Если он оказался на `main` или в основном workspace — **BLOCKED до исправления окружения**, а не «быстро попробую и верну обратно».
4. Codex выполняет один тест, фиксирует метрики и STOP. Web решает `PASS / FAIL / INCONCLUSIVE / NOT RUN` по реальным данным. При успехе **никакой автоматической интеграции**: нужные изменения сначала утверждаются и переносятся в основную разработку отдельной задачей, с тестами.
5. При неудаче Web архивирует экспериментальный чат с кратким выводом, возвращает следующую задачу в **точно названный** `02 — Разработка MVP` / `Codex — MVP разработка`. В `main` не переносится экспериментальный код. Удалить worktree, временные зависимости, модель и тестовые данные можно **только после проверки чужих изменений и твоего явного разрешения**; без автоматического `git clean/reset`, принудительного удаления веток и глобальной деинсталляции. Для сохранения реестра не нужно править `main` посреди теста: можно временно поддерживать копию в источниках ChatGPT Project и синхронизировать продуктовый PROJECT.md после завершения по согласованию.


### Передача файлов из Codex в ChatGPT Web — без ручной свалки

По умолчанию **не пересылай все файлы проекта**. Codex завершает одну задачу **кратким отчётом-указателем**: что сделано, где код и результат, какая ветка/commit SHA, какие реальные проверки с exit code. Web читает уже доступные файлы через GitHub/подключённый источник, если действительно имеет к ним доступ. Не надо создавать отдельный отчётный файл после каждой маленькой правки.

Когда Web нужен именно **файл**, которого нет в доступном источнике, используй один согласованный путь для небольших подготовленных вложений в продуктовом репозитории: `.ai-handoff/<TASK_ID>/`. Например, `.ai-handoff/DATA-SPLIT-01/split-summary.json` (только агрегированные количества, без чувствительных записей). Это **локальный временный каталог**, который следует gitignore-ить при утверждённой настройке продукта; по умолчанию он **не виден ChatGPT Web**. Codex имеет право создавать/копировать туда только файлы, заранее перечисленные в `WRITE ALLOWLIST`, не менять `.gitignore` без разрешения и не перезаписывать чужие данные. Пользователь загружает нужные файлы в **точно названный Web-чат**, указанный в отчёте.

Если хочется читать доказательства непосредственно из GitHub, Web предлагает отдельное разрешение на небольшие **несекретные, проверенные и действительно нужные** файлы под `docs/ai/evidence/<TASK_ID>/` (или согласованным местом), с явным разрешением на сохранение, commit и push. До публикации нет никакой «автоматической синхронизации». **Секреты, полные датасеты, веса моделей, клиентские записи, длинные сырые логи** туда не отправляем. Непроверенный локальный путь и unpushed-коммит — не ссылка для Web.

Пример компактного заключения Codex:

```text
DONE — проверен реальный split датасета, код не изменён.
GIT: experiment/data-split, HEAD <фактический SHA>
VERIFY: python scripts/check_split.py → exit 0; результаты: ... 
EVIDENCE: LOCAL UPLOAD REQUIRED
HANDOFF: .ai-handoff/DATA-SPLIT-01/split-summary.json
КУДА ЗАГРУЗИТЬ: ChatGPT Web → «03 — Эксперимент: проверка датасета»
STOP
```

Это **пример формата**, а не утверждение, что команда, папка или чат уже существуют. Если достаточно существующего исходника GitHub и короткого вывода — `HANDOFF: NONE`. Удаление временных файлов, экспериментальной ветки и worktree после завершения — только после проверки и отдельного разрешения.

### Один раз для нового проекта

1. В ChatGPT Web создай отдельный **Project** для продукта; помести `CORE.md` в **Project Instructions**, а `MANIFEST.md` и нужные материалы держи доступными через GitHub/файлы. Уточни, какая версия реально загружена. Это не обновляется автоматически после каждого коммита методологии.
2. Передай **исходное ТЗ**, а не абстрактное «сделай сайт». Web возвращает вопросы о критических пробелах, краткий MVP/архитектуру, карту пути до хостинга, модельный маршрут и ближайшие срезы.
3. Утверди требования и основные решения. Существующий проект: сначала read-only обследование Codex. Новый: отдельная утверждённая настройка проекта в Codex (AGENTS, Git, запуск, baseline).
4. Дальше используй короткий повторяемый цикл ниже. Не нужно каждый раз создавать новый файл, чат или полный отчёт.

### Сообщения, которые можно копировать

**Старт проекта — в ChatGPT Web:**

```text
У нас новый продукт. Работаем по AI Development OS из инструкций проекта.
ТЗ ниже. Не начинай кодить. Выдели подтверждённые и неясные требования,
предложи самый короткий жизнеспособный MVP и архитектуру без оверинжиниринга.
Дай карту этапов до хостинга, 3–5 ближайших проверяемых срезов, риски,
рекомендации по доступным моделям/effort для Web и Codex.
Задай только вопросы, без которых нельзя принять существенное решение.
Ничего не выдавай в Codex до моего утверждения.
ТЗ: <вставить>
```

**Следующая задача — в ChatGPT Web:**

```text
Вот актуальные проверенные PROJECT/TODO/требования, Git-состояние и итог
предыдущей задачи. Выбери одну следующую вертикальную задачу из согласованного
плана. Если не знаешь файлов — сначала read-only разведка.
Дай один готовый промпт для Codex: цель, READ CONTEXT, WRITE ALLOWLIST,
запреты, приёмка, VERIFY, Git/base, условия BLOCKED и STOP.
Рекомендуй минимально достаточный доступный уровень модели.
```

**Запуск — в Codex Desktop:** открой нужный продуктовый репозиторий, посмотри фактическую доступную модель/default, вставь **один** промпт Web и проверь область изменений. Не передавай весь roadmap как команду к исполнению.

**Приёмка — обратно в ChatGPT Web:**

```text
Вот отчёт Codex, фактический git status/diff, команды и exit codes.
Проверь критерии приёмки и WRITE ALLOWLIST. Отдели подтверждённое
от самоотчёта. Вердикт ACCEPT / FIX / REWORK / INSUFFICIENT EVIDENCE.
Если принятие возможно — кратко обнови прогресс и предложи,
но не запускай, только одну следующую задачу.
```

**Перед хостингом — в ChatGPT Web:**

```text
MVP проверен. Предложи минимальный план staging → production под фактический
стек, бюджет и тип данных: провайдер/лимиты, конфигурация, DNS/HTTPS,
секреты, нужные бэкапы, smoke/health, откат и наблюдение.
Раздели подготовку, тестовый деплой и production на отдельные решения/задачи.
Не выдавай Codex доступ к production и ничего не публикуй без
моего явного согласия.
```

### Важные решения не передаются Codex «на усмотрение»

Если ты обучаешь модель, Web до выдачи задания Codex определяет **что именно нужно утвердить**: train/validation/test пропорции и метод (стратификация, группы, время), единицу разделения и защиту от утечек, seed/версию данных, метрику качества и критерий успеха. Например, **80/10/10 — лишь возможная пропорция, не универсальный закон**. Web показывает альтернативы с последствиями для конкретного датасета; ты утверждаешь политику. Codex уже исполняет её, а не придумывает 42/8/остальное из собственного предположения. Отдельно согласовываются веса классов/объектов, если они влияют на результат: это **не то же самое**, что доли датасета.

В Codex-промпт Web включается `DECISION LOCK` с утверждёнными значениями и источником решения. Если значение отсутствует или данные ему противоречат, Codex отвечает `BLOCKED — CRITICAL DECISION MISSING` **до обучения или изменения сплита**. Допустима отдельная read-only разведка датасета для подсчёта объектов/классов/групп. При выполнении проверки Codex должен показать **фактические** размеры train/val/test, пересечения, состав классов, идентификатор датасета и воспроизводимость разделения. Тестовая выборка не используется для подбора модели/гиперпараметров; обучение преобразований проводится только на тренировочных данных с учётом выбранной методики.

Если ошибочный запуск уже произошёл, **не надо автоматически удалять модель, чекпойнты и результаты**. Сначала read-only аудит реальных конфигов и сохранённых разделений. Если оценка недостоверна или несопоставима с целевым протоколом, Web отмечает `NEEDS REVIEW / NOT COMPARABLE`, утверждает новый протокол и только затем выдаёт отдельную задачу на исправление и повторный запуск в экспериментальной ветке/worktree.

Это правило также относится к значимым изменениям логики авторизации, удаления данных, бизнес-метрик и публичных контрактов. Но мелкие обратимые детали реализации остаются на усмотрение Codex — никаких согласований каждого имени переменной.

## 6. Хостинг: граница ответственности

До выбора хостинга Web должен знать **тип продукта, стек, пользовательские данные, региональные/юридические ограничения, бюджет, трафик, требуемую доступность**. Не навязывай провайдера и не выдумывай цены, тарифы или доступ. Codex может подготовить Dockerfile/конфиг/документацию **только по утверждённому заданию**. Staging и production — разные операции, даже если у малого проекта используется один провайдер.

**Безопасный порядок:** (1) план и способ возврата → (2) ревью конфигурации → (3) staging → (4) реальные smoke-проверки → (5) отдельное «разрешаю production» с названной целью → (6) контролируемый деплой → (7) проверка URL, TLS, ключевых действий и логов → (8) запись фактического результата. Никогда не публикуй реальные секреты в промптах/отчётах; выдавай минимальные права или деплой выполняй сам. `git push`, миграции, удаление данных и изменение production не разрешаются автоматически фактом завершения кода.

Если продакшен-проверка не прошла, **остановись**; решение об откате должно учитывать текущие данные и проверенный способ восстановления. Не применять `git reset --hard` или удаление БД «для очистки».

### Дополнение: проверяем работающее поведение, а не только успешную сборку

**Для страницы тарифов:** Web утверждает структуру и реальные данные тарифов; Codex реализует в своей рабочей ветке. Внутри утверждённой задачи Codex может исправить ошибку разметки и повторить уже разрешённую проверку, но не изменять цены, условия и бизнес-смысл. После реализации проверяется **реальная страница** в доступном безопасном preview/staging: правильные тарифы/валюта, рабочие кнопки и маршрут, разные размеры экрана, доступность и заявленные состояния. По возможности сохранить реальный адрес/снимки/результаты браузерной проверки. Если среда недоступна, `RUNTIME ACCEPTANCE: NOT RUN`; нельзя назвать страницу подтверждённо готовой по одному `npm build`. Для API/CLI/ML вместо браузера используем реальный пользовательский запрос, команду или инференс.

**Для обучения модели:** Web прежде согласует `Model Evaluation Contract`: версию данных, принципы train/validation/test и групп, seed, базовую модель, основные и важные частные метрики, критерий полезного улучшения, запрет подбора по test и порядок сохранения старых checkpoint. Кодекс может выполнить несколько локальных безопасных исправлений в границах задания, но не менять критерии успеха, split или конфигурацию оценки сам. Новый вариант остаётся в отдельном эксперименте, пока результаты не подтверждены и нет отдельного согласия на интеграцию. Для LLM используем набор версионированных пользовательских запросов, границ/нештатных случаев и проверок, а не механически копируем схему split.

**Для передачи через GitHub:** после заранее одобренной задачи и политики публикации Codex показывает реальный `branch + BASE..HEAD + проверенные команды`, делает локальный commit, а push/PR — только если это разрешено для конкретной ветки. Web проверяет, **имеет ли реальный доступ к этой PR-ветке, полному diff и CI**, а не делает вывод по устаревшему `main`. Если доступ частичный, Web запрашивает только недостающий дифф/артефакт; `INSUFFICIENT EVIDENCE` — нормальный промежуточный результат. Защиту `main`, правила ревью, CI и права Codex настраивают и испытывают в **продуктовом** репозитории, а не одним текстом в методологии.

**Самостоятельное исправление:** если в согласованной задаче упал обычный тест, Codex сам исправляет допустимые файлы и перепроверяет. Если требуется новый пакет, изменение теста ради зелёного статуса, незаданный параметр модели, конфигурация безопасности или новый этап графа — остановка и согласование. После повторных бесплодных попыток — диагностика вместо бесконечного цикла.

### Как вводить рекомендации OpenAI/Anthropic без новых обязательных инструментов

Применяй их как **селективные возможности**, а не универсальный стек: 1) проверяемый реальный сценарий; 2) независимый project-native verify/CI; 3) воспроизводимые ML/LLM сравнения при работе с моделями; 4) фактические ограничения разрешений; 5) регрессионные проверки методологии. Playwright, CODEOWNERS, новые агенты, собственная память и дополнительные скрипты не устанавливаются только из-за наличия рекомендаций; нужны подходящий продуктовый контекст, разрешение и проверенный выигрыш.

После реального сбоя связывай `симптом → причина/гипотеза → воспроизводимый тест → исправление → повторный результат` в существующем `TEST_CASES.md` методологии и проектных документах. Замеряй затраченное время, повторы задач, передачи между Web/Codex, реальные проверки и usage-токены лишь когда доступен источник. Не объявляй успешным непрогнанный тест или недоступный CI.

## 7. Как понять, что система помогает, а не тормозит

Для первых реальных задач замерь: сколько ручных переходов между Web/Codex, сколько задач принято с первого раза, сколько выходов за scope, были ли ложные PASS, сколько времени ушло на реальные проверки. Запускай сначала три теста из `TEST_CASES.md`: T03 (маленькая задача), T37+T08 (ловушка scope и независимая проверка), T15 (восстановление контекста). На момент написания всё **NOT RUN**.

### Как система сама выбирает улучшение

После реальной неудачи, повторной переделки, потери контекста или обнаруженного узкого места ChatGPT Web **сам предлагает наиболее перспективное направление** — не ждёт, пока ты назовёшь инструмент. Он сравнивает 2–3 альтернативы, в том числе **оставить как есть**, по ожидаемой пользе, уверенности в гипотезе, цене, простоте проверки, риску и обратимости. Затем рекомендует **только один** минимальный эксперимент: исходное наблюдение, гипотеза, контрольный вариант, метрика, критерий успеха/неудачи, цена и способ отмены. Если проблема не наблюдалась — эксперимент не нужен; если нет исходных данных — первый эксперимент состоит в безопасном измерении.

**Пример с Honcho:** если новые чаты Codex действительно теряют важные решения, сначала измеряем восстановление контекста при текущих `AGENTS.md` + `PROJECT.md`/`TODO.md` на одинаковых тестовых задачах. Только при подтверждённых потерях предлагаем ограниченный эксперимент с Honcho **на вымышленных данных**, с отдельным разрешением на установку и внешнюю передачу информации. Сравниваем число правильных восстановленных решений, ручных подсказок и трудозатраты. Не стало измеримо лучше — Honcho не добавляем.

Web может самостоятельно **выбирать и аргументировать**, но не запускает изменения проекта, платные API, новые зависимости или публикацию без разрешения. Codex получает одну согласованную задачу и останавливается после отчёта. Результат `PASS / FAIL / INCONCLUSIVE / NOT RUN` фиксируется только по реальным данным в уже существующем TODO/Decision либо в тестах методологии, без нового «менеджера экспериментов».

**Не требуется по умолчанию:** отдельный AI-оркестратор, несколько параллельных агентов, обязательный `STATE.md`, новый Skill на каждый этап, отдельный документ для каждой задачи, фиксированное число файлов или новый Codex-чат после каждой правки. Добавлять только после измеренной необходимости.
